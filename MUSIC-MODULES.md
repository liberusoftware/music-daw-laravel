# Music module repositories

Status: under development. Projects core, Media Library core and their optional APIs are installed from modules/ and synchronized to separate repositories. APIs are disabled by default. Projects provides metadata, conditional checkpoint/recovery/import commands and scoped revision polling. Media Library API provides conditional metadata, resumable intake and queued verification/restoration/waveform jobs and short-lived authenticated download URLs; versioned rights/provenance manifests are available; actor-owned offline pin reads, renewal and release are available. Reference-safe trash browsing/commands and queued recovery are available. Core queued private ZIP export with expiry/cleanup is available. Owned archive export HTTP jobs and short-lived private ZIP downloads are available. Core purpose-bound resumable archive intake is available. Core queued archive import with resumable audio progress, cooperative cancellation and atomic pack publication is available. Owned purpose-bound HTTP archive intake and queued import with progress/cancellation/results are available. The host Media Library authorizer rechecks active team membership and workspace-scoped Music permissions for HTTP and worker operations. An opt-in host ClamAV scanner is implemented and verified against the real engine. Production signature updates, transfer-policy/operational integrations and broader module acceptance remain unfinished. The optional Projects Livewire workspace now provides session and track metadata editing, checkpoints/autosaves, reviewed recovery/import, paginated history and explicit draft backups. It is disabled by default; Chromium file/offline/reconnect and narrow-layout regression checks are implemented; wider browser, manual accessibility and production-policy verification remains outstanding. The optional Projects Filament adapter composes that workspace in app/admin panels with a server-selected tenant and a locked scope rechecked on every action, including live foundation workspace status and membership/effective dates in the Music host. It is disabled by default; the Music host now records new revisions and recovery provenance through a transactional foundation audit sink; audit operational acceptance and broader acceptance remain outstanding. Audio Engine Core now has disabled-by-default graph metadata, declared latency plans and project-pinned handoff snapshots with independently enforced 100% package source coverage. Native playback, transport, rendering, migration and hardware verification remain unimplemented; the Core issue remains open. Other Music packages remain planned. Track acceptance and remaining work in the [delivery roadmap](https://github.com/liberusoftware/project-music-daw-laravel-filament/issues/94); no complete DAW release is claimed.

## Host Media Library authorization

When Media Library is enabled at application boot, `MusicModuleIntegrationProvider` installs the host workspace authorizer and pack distribution adapter. Workspace IDs are canonical positive integer foundation team IDs. Active team status and current membership (including effective dates), or active ownership, are required before role permissions are considered. The foundation super-admin role does not bypass membership, suspension or expiry.

Grant explicit `music.media.<operation>` permissions in the `web` guard for the intended team, through the existing foundation roles/permissions administration. Membership and ownership alone grant no Music operation. Read/list, upload, annotate, retain, restore, download, quota_read, pin, pack_read, pack_write, pack_import, pack_export, distribute, pack_distribute, trash_list, trash, collect and archive_cleanup remain distinct operations as used by Core. Token abilities are additional API requirements; they do not replace these permissions. Pack distribution requires its own `music.media.pack_distribute` grant as well as Core's per-asset distribution/provenance checks.

The host requires permission teams mode. Each authorization checks the URL/job workspace rather than the actor's selected tenant, discards cached role/permission relations for the check and restores the previous permission team context on success or denial. Workers therefore evaluate the canonical requester's live grants without inheriting another request's tenant. Uploaded inputs and tasks retain Core's additional ownership rules; verified media is shared only within an authorized workspace. A host adopting finer per-asset sharing must supply its own `MediaAuthorizer` implementation.

Core and API packages retain their public replaceable policy contracts; this host composition adds no domain tables or migrations. Standalone packages remain independent of host users and teams. The host defaults to rejecting scans until its ClamAV driver is explicitly configured as described below; foundation pack transfer approval still needs a host policy. Enabling these authorization adapters does not certify licensing, configure a scanner or complete production deployment.


## Host ClamAV scanner

The host implements the foundation `MalwareScanner` contract with a local ClamAV CLI adapter. The default `MUSIC_MEDIA_SCANNER=reject` denies publication; unknown drivers also reject. Install a supported `clamscan` binary (1.1 or newer, with the documented flags), maintain the official signature database through FreshClam, configure its executable/database paths in the PHP worker environment, then set `MUSIC_MEDIA_SCANNER=clamav`. Rebuild cached configuration and restart supervised workers after changing these settings. No upload can supply scanner flags, a binary path or database location.

| Setting | Default and bounds |
| --- | --- |
| MUSIC_CLAMSCAN_BINARY | `/usr/bin/clamscan`; must be an executable local file. |
| MUSIC_CLAMAV_DATABASE | `/var/lib/clamav`; readable directory containing a readable CVD/CLD database. |
| MUSIC_CLAMAV_TIMEOUT_SECONDS | 20; integer 1–45 seconds, including process startup/database loading. |
| MUSIC_CLAMAV_MAX_FILE_BYTES | 1 GiB + 16 MiB; 44 through 2 GiB minus one byte. |
| MUSIC_CLAMAV_MAX_SCAN_BYTES | 4 GiB; at least the file limit and at most 16 GiB. Counts container and extracted scan work. |
| MUSIC_CLAMAV_MAX_SIGNATURE_AGE_DAYS | 7; integer 1–30 days. ClamAV verifies database age. |

The scanner opens the private input and sends it through stdin with a fixed argument array. Only a zero exit, exact clean receipt and fully consumed input are accepted. Size guards, scan-limit/encrypted-content alerts, archive depth/file-count bounds and a parent process timeout fail closed. Missing tools, absent/stale/malformed databases, invalid settings, detections, unexpected receipts and process failures never publish an asset. Input readers close on every outcome; scanning neither deletes nor moves recordings and does not expose scanner output or private input paths.

ClamAV has an individual-file limit below 2 GiB. Keep configured Core archive intake limits within the scanner's file cap (audio ceiling plus the 16 MiB container allowance); the larger configurable Core ceiling requires another suitable scanner. The scanner child uses bounded streamed PHP input; its own engine memory, temporary disk and database loading still need deployment capacity. Configure asynchronous queue/import budgets for all scans within an attempt, with retry_after above the Core timeout and its lease grace. Rejected transfers keep normal Core quarantine/reservation recovery semantics.

The scanner uses [ClamAV's documented limit alerts and database-age checks](https://github.com/Cisco-Talos/clamav/blob/clamav-1.4.6/docs/man/clamscan.1.in). Signature updating is an operator task; application installation does not download or update production signatures. No application path weakens scan limits or signature validation for tests.

Run `composer test:scanner` after installing `clamav` and the test-only `libfaketime` package. CI installs both and runs actual ClamAV against an unchanged, attributed upstream signed test database plus an EICAR signature. A test-only process factory controls the child clock to verify fresh/stale states; the application clock and production databases remain unchanged. On distributions with a different test library path, set `MUSIC_CLAMAV_TEST_FAKETIME_LIBRARY` to the installed libfaketime shared library. Tests cover clean verified audio, infected archive rejection, stale/malformed databases, timeout/startup faults, incomplete input and byte/configuration limits. These fixtures are not production signatures.

## Media worker deployment budgets

Horizon requires `QUEUE_CONNECTION=redis` and a supervised Horizon process. The example environment keeps the host's database queue default; installing Music does not enable asynchronous production workers. Never use the synchronous connection for production archive imports.

Keep the job timeout strictly below `HORIZON_WORKER_TIMEOUT`, and keep that supervisor timeout strictly below `REDIS_QUEUE_RETRY_AFTER`. Archive imports also require retry_after strictly above their configured timeout plus the 15-second lease grace. Defaults are 60-second jobs, a 75-second Horizon supervisor and a 90-second Redis retry interval. For a 300-second import budget, use `MUSIC_MEDIA_ARCHIVE_IMPORT_TIMEOUT_SECONDS=300`, `HORIZON_WORKER_TIMEOUT=315` and `REDIS_QUEUE_RETRY_AFTER=330`. Apply these values consistently to every worker deployment and queue producer; environment-specific Horizon overrides must preserve the same ordering. Other queue connections need their own retry/visibility settings.

Rebuild configuration with `php artisan config:cache` and gracefully terminate Horizon with `php artisan horizon:terminate` under a process supervisor after configuration changes. Allow the supervisor's shutdown grace to exceed the longest job budget so deployment does not kill active imports. Run module migrations before starting new workers. Drain workers before schema rollback; prefer forward recovery for already collected recordings. A failed/expired import must be retried through its original request identity to obtain a new fenced dispatch; blindly redelivering an old queue payload does not reclaim its lease.

These timeout defaults do not provision Redis, process supervision, maintained scanner signatures, authorized cleanup scheduling or transfer approval. Validate those services and capacity on the deployment host before enabling intake.

## Host cancelled-upload collection

The host command `php artisan music:media:collect-quarantine WORKSPACE_ID USER_ID` runs one Core collection page, with a default dry-run report. The actor must be an existing host user with current active workspace membership and the workspace's `music.media.collect` permission. Shell access does not bypass that policy. The Media Library module must be enabled and migrated; the command refuses to bootstrap disabled domain services.

Inspect the JSON report before executing the same arguments with `--execute`. Each invocation examines at most `--limit=100` eligible chunks (allowed range 1–100); `--grace-hours=24` is the minimum cancellation age, up to 8760 hours. Active intake, published recordings and recent cancellations are excluded by Core. The command neither cancels uploads nor collects ready/trashed recordings or untracked physical objects. Its output contains chunk IDs, declared bytes, cutoff and cursor, with no storage paths or filenames.

For multiple pages, pass the previous successful report's non-null `next_chunk_id` as `--after=CHUNK_ID`. A null cursor ends the sweep. Start the next scheduled sweep from zero so newly eligible earlier chunks are reconsidered. A dry-run cursor is only a preview: start execution from the original cursor. On nonzero exit, keep the last successful execution cursor and retry after resolving the failure; a failed page emits no new cursor. Core acknowledges already-missing objects, and releases reservations only when the final cancelled chunk is acknowledged. Failed physical deletion leaves the ledger and reservation available for retry.

To schedule bounded progress, configure the deployment scheduler to run an explicitly chosen actor/workspace command with `--execute --limit=100 --no-interaction`, beginning at zero each time. Serialize runs for that workspace using the scheduler's overlap lock, monitor nonzero exits and disk/quota backlog, and size frequency/capacity for incoming cancellations. For a complete sweep per run, the operator must persist and advance only successful cursors as described above. No actor, workspace or deletion schedule is enabled automatically. This command does not schedule archive artifact cleanup or explicit published-asset collection.

## Host private ZIP artifact cleanup

Run `php artisan music:media:cleanup-archives WORKSPACE_ID USER_ID --execute --limit=100 --no-interaction` as an explicitly selected operator identity. Core requires current workspace membership and the distinct `music.media.archive_cleanup` permission; `collect`, upload, export permission or ownership alone does not authorize cleanup. The module must be enabled and migrated. The command requires `--execute` on every invocation: Core provides no preview for this action, so omitting that flag exits without collection rather than presenting a dry-run report.

Each batch removes at most 1–100 artifacts belonging to the selected workspace: expired ready exports or failed/cancelled staging older than one day. Active queued/running work, unexpired ready ZIPs, source recordings, packs, retention and reservations are preserved. The JSON result reports `schema_version`, `workspace_id` and `cleaned_artifacts`, without paths or task/pack contents. A zero count means no currently eligible artifacts; repeat successful bounded batches to drain a backlog. No cursor is needed because acknowledged tasks become expired and leave the eligible set.

Schedule explicitly with overlap protection per workspace and a shared scheduler lock on multiple servers. Monitor nonzero exits and artifact disk usage. On failure, retry the same workspace and limit after resolving the reported error: physical deletion can precede SQL acknowledgement, and Core acknowledges already-missing artifacts on retry. Failed commands emit no success count. Core owns the one-hour ready-export expiry and one-day staging grace; this host command does not shorten them or collect untracked storage objects. No public deletion endpoint or automatic production schedule is installed.
